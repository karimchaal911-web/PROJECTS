\section{Operator-centred dashboard design}

The dashboard is the point at which process, quality and model evidence become a supervision aid. Its design priorities are state visibility, hierarchy and restrained alarm colour. Normal status uses green, low/medium attention uses amber, high anomaly uses red and unavailable/data-quality conditions use grey. Colours never replace text: each state is also labelled. The two pages separate routine monitoring from diagnostic investigation so that explanations do not overload the main view.

The PBIP uses a DirectQuery semantic model and a deliberately configured five-second automatic page refresh on both pages. Repository validation reports 86 total visuals, 114 field references and 276 model fields across five tables; all field references, navigation actions, refresh settings, ordering and query budgets resolve \cite{pbivalidation}. The interval is a prototype visualization target, not the native plant measurement frequency. Deployment to Power BI Service would still require an appropriate capacity/gateway design, credentials and performance measurements under expected concurrency \cite{powerbiautorefresh}.

\begin{decisionbox}[Dashboard visual source]
The two figures in this chapter are the final validated 16:9 project renders generated from the SQL-backed preview workflow. They reproduce the final two-page PBIP information architecture without the Power BI Desktop ribbon, authoring panes or credentials. They are faithful layout/value proxies rather than evidence of a deployed Power BI Service application.

\section{Page 1: Operations Overview}

\Cref{fig:pbi-overview} presents the overview page. Its PostgreSQL demonstration data come from the held-out chronological TEST interval of the canonical source, not from a separately generated dashboard dataset. The upper cards answer immediate operating questions: current predicted moisture, latest laboratory moisture and age, anomaly risk/status and operational severity. Process tiles expose key thermal, flow, feed, steam and vacuum measurements. Trend panels maintain time context rather than reducing the process to one current value. Laboratory markers remain sparse, while the prediction continues at each prototype replay step.

The captured state deliberately demonstrates freshness handling: the header reports data freshness separately from process status, and the last stored diagnosis remains visible as context. This is not an application failure. It shows that old data are not presented as proof of current operation. The static \texttt{PROTOTYPE · REPLAY} indicator and \texttt{Replay / Refresh: 5 s} wording make clear that five seconds is the demonstration cadence, not native plant acquisition.

The latest-lab presentation is deliberately paired with age. Without age, a carried-forward result could appear current. In this synthetic prototype, validated error is computed only where a represented sparse laboratory observation and a corresponding prediction coexist. The principal distinction is therefore visible in both model and interface:
\begin{itemize}
\item \textbf{predicted moisture}: continuous model estimate;
\item \textbf{latest laboratory moisture}: last available measured value with timestamp/age;
\item \textbf{validated error}: prediction minus laboratory value only at a sample timestamp.
\end{itemize}

DirectQuery measures aggregate only the intended grain. A lightweight eight-hour PostgreSQL view feeds the overview trends, avoiding an expensive latest-lab as-of lookup for every historical point. The report validator also enforces a query-visual budget, which reduces the risk that the selected rapid page refresh launches an unnecessarily large set of source queries.

\section{Page 2: Diagnostics and Root Cause}

The diagnostic page in \cref{fig:pbi-diagnostics} supports investigation after an anomaly is raised. A timeline provides event context; filter controls support event selection; status fields show the probable subsystem, diagnosis, causes and verification guidance; contributor tiles display direct abnormal variables with direction and severity. The wording remains explicitly advisory.

\begin{figure}[p]
\centering
\includegraphics[width=\textwidth]{powerbi_diagnostics.png}
\caption{Final SQL-backed Diagnostics and Root Cause page with event context, ranked contributors and verification guidance.}
\source{MAP-Dryer-AI final academic-showcase dashboard render; Author's work.}
\label{fig:pbi-diagnostics}
\end{figure}

The selected synthetic event is labelled medium severity and assigned to the feed-loading subsystem. Wet-product feed rate and product-inlet temperature lead the contributor ranking, while residence time is the only displayed high univariate deviation. This combination demonstrates why the page shows several pieces of evidence and a verification prompt: the subsystem label is a reasoned prioritization, not proof of a root cause.

Consecutive anomalous prototype rows separated by at most 30 seconds are grouped into one event. This limits alarm flooding and gives the operator an episode rather than a list of near-identical timestamps. Severity, subsystem and diagnosis for an event are taken from its peak-risk row. The raw score is retained for technical traceability; the risk scale is used for visual interpretation.

\section{Dynamic status and selected measures}

The semantic model groups measures by current values, lab context, validation, risk/status, trends, critical variables and events. The interface answers three questions in order: \textbf{what is happening}, through process/moisture/lab state; \textbf{where evidence is concentrated}, through direct contributors and subsystem voting; and \textbf{what should be verified}, through cautious diagnosis and an inspection prompt. Unavailable information is displayed as a dash or explicit state rather than zero, and \code{DATA\_QUALITY} is never styled as an equipment anomaly.

\subsection{Semantic model and DAX logic}

The five semantic tables preserve different grains: one row per process timestamp, recent trend point, true laboratory sample, grouped anomaly event, or ranked event contributor. This prevents contributor joins from multiplying process rows and prevents carried-forward lab context from increasing the sample count. Latest-lab age uses the true lab timestamp and latest process timestamp:

\begin{minipage}{\textwidth}
\begin{lstlisting}[caption={Simplified DAX pattern for laboratory-result age.}]
Lab Result Age Minutes =
IF (
    ISBLANK ( [Lab Last Sample Timestamp] ) ||
    ISBLANK ( [Latest Timestamp] ),
    BLANK (),
    DATEDIFF ( [Lab Last Sample Timestamp],
               [Latest Timestamp], SECOND ) / 60.0
)
\end{lstlisting}
\end{minipage}

Freshness has precedence: absent or old data produce \code{STALE} even if the last stored anomaly state was normal; otherwise anomaly, watch and normal states are evaluated. The palette never replaces the text label. Although a critical colour exists for display compatibility, the Python engine does not assign \code{CRITICAL}; its reference-profile quantiles are statistical and not approved safety limits.

\section{Illustrative operator-use scenario}

In a synthetic replay episode, the operator first checks lab-result age and treats the soft-sensor value as an estimate. The trend is then reviewed for coincident changes in air, feed or steam. After selecting the event, ranked contributors and subsystem voting prioritize a verification. For example, low air flow and fan speed may prompt inspection of fan operation, flow instrumentation and exhaust condition. PCS7, approved limits and field information remain authoritative; the model neither changes a setpoint nor acknowledges an alarm.

\section{Usability and performance considerations}

The current pages are suitable for a controlled demonstration. Industrial use requires operator testing, accessible colour/text cues, terminology aligned with the site alarm philosophy, approved limit ownership and review of nuisance events. Model monitoring should track version, lab error, missing inputs, stale duration, event rate and drift; retraining must follow a versioned approval process. PostgreSQL, gateway and report-query p95/p99 latency must be tested under expected concurrency. The five-second visualization refresh is retained only if end-to-end measurements justify it \cite{powerbiautorefresh}.

\begin{engineeringbox}[Dashboard contribution]
The dashboard centralizes the operational narrative without obscuring provenance: process values remain process values, laboratory results retain age, predictions remain estimates, anomaly risk remains statistical and diagnosis remains a verification aid. That semantic discipline is the principal usability achievement of the Power BI layer.
\end{engineeringbox}
