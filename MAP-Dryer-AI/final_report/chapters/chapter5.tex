\chapter{AI Models: Moisture Prediction and Anomaly Diagnosis}
\label{chap:models}

\section{Two complementary supervision functions}

The project contains two principal modelling components. The supervised soft sensor estimates final moisture, while the unsupervised component examines every row of the chosen prototype replay grid for novelty relative to a reference regime. A deterministic diagnostic layer then translates an anomalous observation into physical evidence. Prediction answers ``what moisture is expected?''; novelty detection answers ``does the operating pattern resemble the reference?''; diagnosis answers ``what should be checked first?''

\section{Chosen moisture model and evidence contract}

Notebook 03 is the single source of truth for both the reported moisture experiment and the runtime soft sensor. It reads \code{data/processed/MAP\_Dryer\_Lab\_Aligned\_16.csv}, the 1,103-row handoff produced by Notebook 02 from the canonical 92-day source. The data are split chronologically into 772 TRAIN, 166 VALIDATION and 165 untouched TEST rows. The runtime subsequently computes and orders the same 16 original named features and loads the exact Notebook 03 artifact.

The contract uses nine direct process variables, the five engineered features defined in Notebook 02, and the most recent strictly previous laboratory density and final-product-temperature values. Final moisture remains the target and is never an input. Standardization is fitted inside each training fold. Five-fold expanding \code{TimeSeriesSplit} on TRAIN tunes candidate hyperparameters, the later VALIDATION segment selects the model family, and TEST is opened once after selection and refitting on TRAIN plus VALIDATION.

\section{Candidate comparison and Ridge selection}

Five candidates are evaluated under the same forward-looking structure. Ordinary Linear Regression provides a transparent reference. Ridge tests L2 shrinkage. Elastic Net tests combined L1/L2 regularization, while Random Forest and Gradient Boosting test nonlinear mappings. Each candidate's tuning remains inside TRAIN; its fitted best configuration is then scored once on VALIDATION.

Ridge gives the lowest VALIDATION RMSE, 0.0013566 percentage points, narrowly ahead of Elastic Net at 0.0013625 and Linear Regression at 0.0013671. Selection is therefore supported by a later unseen segment, not by the final TEST score. Notebook 03 also contains separate Elastic Net training and metrics cells, matching the other baseline models. The selected tuning structure is:

\begin{lstlisting}[language=Python,caption={Leakage-safe Ridge pipeline and tuning grid.}]
ridge = Pipeline([
    ("scaler", StandardScaler()),
    ("model", Ridge()),
])

search = GridSearchCV(
    ridge,
    param_grid={"model__alpha": [0.01, 0.1, 1, 10, 100]},
    cv=TimeSeriesSplit(n_splits=5),
    scoring="neg_root_mean_squared_error",
)
\end{lstlisting}

\section{Model interpretation and risk}

The Ridge model consumes all 16 governed inputs. \Cref{fig:ridge-interpretation} reports absolute standardized coefficient magnitudes.

\begin{figure}[htbp]

\source{Executed Notebook 03 figure outputs \cite{moisturenotebook}.}

Air per feed and wet-product feed rate have the largest absolute standardized coefficients, followed by cooler-air and dryer-air temperature. Correlated inputs can redistribute weight, and coefficient magnitude does not establish causation.

$R^2$ describes explained variation in this particular holdout sequence; it does not show whether errors are acceptable against an approved product specification. MAE describes average absolute deviation, RMSE penalizes larger misses, and the time/residual plots expose local behaviour. Industrial validation must also quantify analytical uncertainty, performance by campaign and grade, uncertainty coverage, drift, and errors near approved product limits.

L2 shrinkage controls the correlated 16-feature contract, yet it cannot compensate for an unrepresentative dataset or extrapolation outside training support. Any real-data study must rebuild the comparison rather than assume that Ridge or this hyperparameter remains optimal.

\section{Novelty detection and risk display}

Notebook 04 is the authoritative source for the anomaly runtime export. Its final cells use a One-Class SVM with an RBF kernel, \code{gamma='scale'} and $\nu=0.02$ \cite{anomalynotebook,oneclasssvm}. It is fitted on a deterministic 6,000-row sample from the 1,111,681 process rows in the canonical TRAIN period and checked on a separate 20,000-row validation sample. The observed validation flag rate is 5.925\%. This is a novelty-rate diagnostic on supplied synthetic process patterns, not a false-positive rate or fault-detection accuracy because no confirmed plant fault labels exist \cite{trainingreport}.

The raw decision function is not a probability. A logistic mapping converts it to a display risk in $[0,1]$, with 0.5 at the detector boundary and 0.8 used as a high-risk display threshold. This improves dashboard readability but does not create a statistically calibrated failure probability.

\begin{lstlisting}[language=Python,caption={Final service mapping from SVM output to display risk.}]
score = float(anomaly_model.decision_function(scaled)[0])
anomaly_detected = int(anomaly_model.predict(scaled)[0]) == -1
risk = 1.0 / (1.0 + math.exp(
    min(max(score / risk_scale, -60.0), 60.0)
))
\end{lstlisting}

For a normalized feature vector $\mathbf{x}$, the RBF One-Class SVM learns a boundary around the reference observations. The scikit-learn decision function is positive on the accepted side and negative on the novelty side; the service consequently raises the anomaly flag below zero. The parameter $\nu=0.02$ acts as a design control on training errors/support vectors rather than a guaranteed future anomaly rate \cite{oneclasssvm}. The observed validation flag rate is therefore reported, not assumed.

The reference profile and SVM serve different purposes. The SVM evaluates the joint multivariate pattern. Robust univariate quantiles identify which individual features are unusual enough to explain the event. A row can be novel even when no single raw variable exceeds a percentile limit, because the combination is unusual; in that situation the service assigns low severity and states that no direct abnormal contributor was found. Conversely, a raw variable outside its 99th percentile supports a high operational-severity display only when the multivariate detector has also flagged the observation.

\section{From anomaly to operator-readable diagnosis}

The real-time diagnostic engine uses a train-period reference profile containing median, MAD, IQR and 1st/5th/95th/99th percentiles per feature. A robust scale is computed as the maximum of scaled MAD, scaled IQR and a numerical floor. Each feature receives a direction and variable severity: values inside the 5th--95th percentile band are normal, values between the 1st/5th or 95th/99th limits are medium deviations, and values beyond the 1st or 99th percentile are high deviations. Robust distance is multiplied by feature criticality to rank evidence.

Engineered features participate in subsystem voting, while only raw process features are returned as operator-facing contributors. A feature associated with multiple subsystems divides its score among them. The selected subsystem is the one with the greatest accumulated contribution. A transparent rule map produces a cautious diagnosis and recommended verification for the leading direct contributor. Event severity is \code{LOW} when no direct abnormal contributor exists, \code{MEDIUM} for at least two medium deviations, and \code{HIGH} when at least one direct feature exceeds its 1st/99th percentile range. \code{CRITICAL} is deliberately not assigned because statistical quantiles are not approved alarm or trip limits \cite{diagnosisconfig,projectrepo}.

The broader configuration-driven diagnostic work defines eight concise rule families: insufficient drying air, insufficient thermal supply, dryer overload, reduced cooling, abnormal exhaust/pressure, possible temperature-sensor bias or jump, possible stuck sensor, and process instability or oscillation \cite{diagnosisconfig}. Air/fan evidence leads to supply and measurement checks; steam/thermal evidence leads to heating checks; feed, residence and ratio evidence leads to loading checks; and cooler, vacuum or temporal evidence directs the remaining subsystem checks. These rules informed validation scenarios, but the final replay service uses its dedicated quantile/ranking engine. This distinction prevents evidence from one implementation path being attributed to another.

These rules are deliberately phrased as hypotheses. A low air-flow reading can represent a true delivery problem, a closed damper, an exhaust interaction or a biased instrument. The display therefore separates probable diagnosis, possible causes and recommended verification. In a future feedback loop, confirmed causes could be used to evaluate precision by rule; the current synthetic scenarios test logical acceptance, not empirical causal accuracy.

\section{Artifacts, traceability and failure behaviour}

One governed artifact set is deliberately visible. Notebook 03 saves the selected moisture pipeline and JSON evaluation record; Notebook 04 saves the anomaly model, scaler, reference profile and its evaluation record. The runtime loads those exact governed artifacts from \code{models/5s}, while the shared schema records both ordered feature contracts. Runtime versions travel with database outputs and feature order is checked at inference. Invalid or incomplete input produces \code{DATA\_QUALITY}; insufficient shifted history produces an unavailable prediction with a reason. These are essential production-engineering behaviours: a system must reveal which compatible artifact it used and when it could not reason safely.

\begin{engineeringbox}[Meaning of explainability]
The diagnostic output is evidence localization, not proven causality. ``Likely subsystem'' means that abnormal, criticality-weighted features assigned to that subsystem dominate the current observation. ``Recommended verification'' tells the operator what to inspect; it is not a command or maintenance conclusion.
\end{engineeringbox}
