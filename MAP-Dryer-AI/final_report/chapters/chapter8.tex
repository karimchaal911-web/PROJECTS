\section{Validation strategy}

Validation operates at several levels. Unit and integration-contract tests cover timestamp parsing, selected-grid checks, residence-time alignment, prevention of future-row use, exact ordered feature consistency, artifact inference, deterministic generation and hashes, finite replay defaults, structured database configuration, anomaly mapping, diagnostic rules, temporal patterns, subsystem scoring, severity, feedback and database/runtime helpers. The final run passed 33 tests plus 8 subtests with zero failures \cite{testrecord}. Execution time is deliberately omitted because it varies with machine load and is not a performance acceptance measure.

Integration evidence includes canonical replay contracts and database views. The final live verifier reads physical \code{sourceColumn} bindings from all five current TMDL tables and compares them with the PostgreSQL views. Dashboard and overview each exposed 1,500 version-filtered rows and the lab view two rows; contributors and events were empty because the bounded v6 interval contained no anomaly flags, which those optional evidence views allow. All required column contracts passed. These checks give confidence that the committed artifact is internally coherent. They do not replace load, usability or failure-recovery tests in an OCP-managed environment.

\section{What the prototype demonstrates}

The work demonstrates six feasibility points:
\begin{enumerate}
\item a multi-rate stream can preserve sparse quality measurements while supporting inference on the selected near-real-time replay grid;
\item residence-aware process snapshots and strictly previous laboratory inputs can prevent obvious target leakage;
\item model selection and holdout results can be versioned and reproduced;
\item novelty evidence can be converted into cautious, subsystem-oriented guidance;
\item idempotent storage and purpose-built views can support a frequent DirectQuery workload; and
\item one dashboard can organize process, quality, risk and diagnosis without implying autonomous control.
\end{enumerate}

This is a meaningful Industrial Engineering contribution because it organizes the complete production-information loop. The technical value lies not only in the model score but also in data semantics, traceability, latency, operator interpretation and explicit decision authority.

\section{Limitations}

The following limitations are material, not footnotes:
\begin{itemize}
\item \textbf{No live PCS7 connection.} The industrial screens informed process understanding, but CSV replay substitutes for PCS7/historian acquisition.
\item \textbf{Synthetic final demonstration data.} Relationships, anomaly episodes and metric values may be more regular than plant behaviour.
\item \textbf{Limited real historical data.} Real grade changes, campaigns, equipment states, calibration events and rare faults are not represented at industrial scale.
\item \textbf{Simulated lab timing.} The two-hour sparsity mirrors observed availability, but laboratory logistics, delays and re-tests are simplified.
\item \textbf{Prototype visualization interval only.} The five-second grid and refresh were deliberately selected for simulation; they do not describe native instrumentation sampling. Development-machine timing also excludes plant networks, gateways, concurrent users, service throttling and high availability.
\item \textbf{Statistical diagnostic limits.} Percentile bands are not approved operating, alarm, safety or trip limits; diagnosis is not causal proof.
\item \textbf{No closed-loop control.} The prototype neither recommends immediate setpoint changes nor commands any actuator.
\end{itemize}

Effective sample size remains a central limitation. The canonical stream contains 1,589,760 process rows, but two-hour laboratory cadence provides 1,104 sparse targets and only 1,103 supervised rows after the initial insufficient-history sample is removed. Label cadence determines supervised information; dense process rows must not be counted as independent quality labels. The single supplied synthetic chronology, despite its TEST $R^2$ of about 0.825, still requires representative plant campaigns before any accuracy or stability claim can be generalized.

{\small
The first future step is data, not control. An approved historian extract should cover normal campaigns, operating modes, grades, maintenance states, instrument quality flags and laboratory timestamps. Variable names, units, sampling behaviour and approved operating envelopes should be reconciled with production and laboratory experts. Models should then be retrained and evaluated by campaign and time period, with uncertainty, drift and false-alarm cost explicitly reviewed.

Second, the existing registry, hashes, finite replay defaults and environment validation should be extended into managed deployment controls: authenticated read-only acquisition; network segmentation; an approved secrets manager; redundant or recoverable PostgreSQL; health checks; retention rules; centralized structured logging; registry-backed promotion and rollback; latency and drift monitoring; backup/restore tests; and Power BI gateway/capacity qualification. A shadow-mode period should compare the solution with PCS7 and laboratory results while it has no operational authority.

Third, diagnosis should improve through representative failure scenarios and operator feedback. Each displayed event can be reviewed as confirmed, rejected or unresolved, with comments and actual cause when known. This can support rule refinement and false-alarm reduction. Alert-management logic should suppress repetitions, respect acknowledged plant states and align with OCP procedures.

Only after real-data validation, safety engineering, cybersecurity approval, operator studies and robust fail-safe design should any recommendation/control architecture be investigated. Even then, a staged advisory or supervisory recommendation layer is more appropriate than immediate autonomous control. OCP operating authority and approved safety systems must remain decisive.

\noindent\textbf{\color{DeepBlue}Recommended next gate.}
Run the current software in read-only shadow mode against an approved historian extract, retain laboratory truth unchanged, and conduct joint weekly reviews with production, process, laboratory and automation stakeholders. Progress to operational use only when accuracy, false-alarm burden, timing, failure handling and human factors have documented acceptance criteria.
}
